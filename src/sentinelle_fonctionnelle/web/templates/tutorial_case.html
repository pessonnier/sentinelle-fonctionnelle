Tutoriel guidé

Configurer et rédiger un cas de test

De la cible web au workflow structuré prêt pour la génération Playwright.

Étapes Repères d’interface 1. Configurer le projet 1 bis. Configurer le LLM 2. Préparer le cas 2 bis. Traduire les préconditions 3. Utiliser l’assistant 4. Analyser une page 5. Rédiger les étapes 6. Paramétrer les données 7. Finaliser avec le LLM 8. Vérifier la structure 9. Enregistrer

Avant de commencer

Se repérer dans l’interface

Chaque catalogue présente les éléments existants avant le formulaire de création. Utilisez le bouton + Ajouter… sous la liste : le formulaire s’ouvre sur toute la largeur et le premier champ reçoit le focus. Le bouton − ou la touche Échap le replie sans effacer ce que vous avez commencé à saisir.

Le sélecteur Thème de l’en-tête permet de choisir Forêt, Océan, Prune, Coucher de soleil, Graphite, Contraste élevé ou Défense — ministère des Armées. Le choix est conservé par ce navigateur et n’influence jamais les tests ni leur code.

Étape 1

Configurer le projet

  1. Depuis l’accueil, utilisez + Ajouter un projet, puis saisissez un nom métier explicite.
  2. Indiquez la cible web autorisée, par exemple https://recette.example.net.
  3. Choisissez une politique de sécurité qui interdit les autres origines.
  4. Dans le projet, utilisez + Ajouter un plan de test et sélectionnez son profil d’approche versionné.
  5. Pour corriger le projet, revenez au catalogue et dépliez Modifier le projet à côté de sa carte. Si sa cible change, contrôlez séparément les plans existants.
  6. Dans la page du projet, construisez directement l’arborescence Plan → Dossier → Suite → Cas avec les boutons + de chaque niveau.
  7. Ajoutez une suite, puis le cas de test à rédiger.

La cible du projet définit la frontière de l’analyse. Une page située sur une autre origine est refusée avant tout téléchargement.

Préparation de la génération

Configurer l’accès LLM et le code attendu

  1. Ouvrez Accès aux LLM.
  2. Utilisez le bouton + Ajouter une nouvelle connexion sous la liste, puis indiquez le fournisseur et l’URL de base.
  3. Dans le champ Modèle, utilisez ↻ pour charger la liste exposée par cette URL, puis choisissez l’identifiant attendu.
  4. Saisissez uniquement le nom de la variable contenant la clé, par exemple OPENAI_API_KEY.
  5. Définissez cette variable dans l’environnement qui lancera l’application ou le futur worker. Ne copiez jamais sa valeur dans le formulaire.
  6. Ouvrez ensuite Génération de code, utilisez + Ajouter un profil de génération et liez-le à la version de cet accès.
  7. Choisissez le langage, le framework, le répertoire relatif, les motifs de fichiers et les validations autorisées.
  8. Dans le cas de test, sélectionnez les deux références versionnées avant de confirmer la structure.

Utilisez proposal-only pour produire un candidat sans remplacer de fichier. Les contrôles sont choisis dans une liste fermée ; aucune commande shell libre ne doit être confiée au modèle.

Configuration locale Ollama utilisée

  1. Vérifiez le service avec http://127.0.0.1:11434/api/version.
  2. Dans Accès aux LLM, utilisez le fournisseur ollama, l’URL http://127.0.0.1:11434/v1 et le modèle exact qwen3.6-35b-a3b-q4_K_M_128k:latest.
  3. Laissez la variable de clé vide uniquement pour la boucle locale et fixez le délai à 600 secondes.
  4. Laissez d’abord le profil désactivé puis cliquez sur Tester la connexion et le JSON.
  5. Activez une nouvelle version du profil seulement lorsque le test complet, avec le contexte déclaré, réussit.

Le test utilise un contrat synthétique : aucune information du cas n’est envoyée. La documentation complète et le diagnostic matériel observé se trouvent dans docs/llm/ollama.md.

Étape 2

Préparer le contexte du cas

Objectif
Un seul comportement métier à démontrer.
Acteur métier
Le rôle compréhensible dans la documentation.
Profil d’acteur
La fixture d’authentification non secrète utilisée par le runner.
Profil d’environnement
La configuration versionnée qui résout l’URL, la locale, le navigateur et les origines.
Page de départ
La première page ouverte par le parcours.
Préparation
Les états et fixtures nécessaires avant la première action.
Nettoyage
La remise en état qui rend le cas réexécutable.

Ne saisissez jamais de mot de passe. Utilisez uniquement une référence telle que client-password.

Avant les étapes

Traduire et confirmer les préconditions

  1. Saisissez une condition métier autonome par ligne, sans décrire sa solution technique.
  2. Cliquez sur Préparer les traductions. Une carte non confirmée est créée pour chaque ligne.
  3. Choisissez sa nature : condition vérifiable, fixture, dépendance technique, préparation ou nettoyage.
  4. Pour une fixture ou une dépendance, renseignez sa référence non secrète. Une fixture doit aussi être ajoutée dans Données de test référencées.
  5. Reformulez précisément la traduction, puis cochez sa confirmation. Toute modification ultérieure la décoche.
  6. Dans Structure envoyée au générateur, cliquez sur Vérifier la préparation.

Le contrôle est local et déterministe. Il vérifie l’origine de la cible, les traductions, les fixtures, la seule présence des secrets et le runtime Playwright. Il n’affiche jamais la valeur d’un secret et le LLM ne peut pas convertir un échec en réussite.

Compatibilité

Les workflows historiques de version 1 restent lisibles. Dès qu’ils sont réenregistrés par le nouvel éditeur, la version 2 exige cette revue avant la génération.

Étape 3

Utiliser l’assistant de conception

  1. Dans le cas de test, ouvrez la section Assistant.
  2. Sélectionnez l’intention qui correspond à un seul comportement métier.
  3. Cliquez sur Analyser les informations manquantes.
  4. Lisez chaque question et surtout la ligne Utilité, qui explique l’impact de la réponse.
  5. Utilisez Compléter le champ concerné pour revenir directement à la bonne zone du formulaire.
  6. Relancez le diagnostic après vos modifications pour voir la complétude progresser.

Exemple : pour « Se connecter avec succès », l’assistant recherche l’acteur, la page de connexion, les références d’identifiants, les actions de saisie et une preuve visible de l’ouverture de session. Il ne vous redemande pas une information déjà présente dans la structure.

À retenir

Le pourcentage de complétude signifie que les rubriques attendues sont renseignées. Il ne signifie pas que le cas est validé, que la page fonctionne ou que du code a déjà été généré.

Étape 4

Analyser une page

  1. Copiez l’URL de la page dans le champ Page à analyser.
  2. Cliquez sur Analyser la page.
  3. Relisez les champs, boutons, liens et titres affichés dans la palette.
  4. Cliquez dans une cible d’action ou de validation, puis sur une carte de la palette pour insérer sa référence.

Une référence comme page:login#email ne constitue pas un sélecteur CSS. Elle conserve le libellé, le rôle et la stratégie de localisation proposés. Le générateur doit encore contrôler l’unicité et la stabilité du localisateur.

Comprendre les suggestions issues de la page

Revenez dans la section Assistant après l’analyse. Le panneau Ce que les champs HTML permettent de faire distingue :

  • les éléments manipulables, avec leurs actions compatibles ;
  • les éléments observables, avec leurs validations possibles ;
  • les exemples de valeurs issus des options HTML ou des espaces de noms de données ;
  • les éléments uniquement destinés à une validation, comme un titre.

Cliquez d’abord dans la cible d’une carte d’étape, puis sur Utiliser cette référence. La référence est insérée sans transformer le libellé métier en sélecteur CSS fragile.

L’analyse HTML statique n’utilise pas de session ni de secret. Pour une page rendue par JavaScript ou protégée par authentification, utilisez le plan déclaratif de l’exploration contrôlée Playwright décrit ci-dessous.

Cataloguer une page après connexion

  1. Créez un plan JSON versionné avec l’URL de départ, l’URL finale à cataloguer et une liste fermée d’actions.
  2. Référencez une ligne XLSX synthétique avec son identifiant de source, sa colonne clé et sa clé de ligne.
  3. Utilisez des valeurs comme {% raw %}{{data.login.email}}{% endraw %} : les valeurs résolues ne sont pas écrites dans le catalogue.
  4. Lancez analyze-rendered-page depuis un processus local distinct de l’application web.
  5. Relisez discovery.rendered_only_references pour identifier ce que JavaScript a ajouté.
  6. Appliquez le catalogue à une copie du workflow avec apply-page-catalog ; l’opération est refusée si une cible utilisée disparaît.
.\.venv\Scripts\python.exe -m sentinelle_fonctionnelle.cli analyze-rendered-page `
  --plan .\config\examples\hr-demo-rendered-page-plan.json `
  --base-url http://127.0.0.1:8775 `
  --output .\outputs\hr-demo\catalog-saisie-manager.json

.\.venv\Scripts\python.exe -m sentinelle_fonctionnelle.cli apply-page-catalog `
  --catalog .\outputs\hr-demo\catalog-saisie-manager.json `
  --workflow .\config\examples\hr-demo-workflow.json `
  --output .\outputs\hr-demo\hr-demo-workflow.rendered.json
Pourquoi un plan fermé ?

Le navigateur accepte au plus vingt actions et ne sait ni exécuter un script libre ni quitter l’origine locale. Le HTML source et les valeurs saisies ne sont jamais conservés dans l’artefact.

Étape 5

Ajouter et ordonner les étapes

Choisissez d’abord le mode qui correspond au niveau de précision dont vous disposez. Les trois modes alimentent la même structure de génération : vous pouvez commencer en texte puis accepter une proposition structurée.

Formulaires action et contrôle
Pour une saisie précise : une carte décrit le contexte, l’action, sa donnée et le contrôle. Utilisez Ajouter un contrôle à la suite lorsqu’une action exige plusieurs observations.
Un texte par étape
Ajoutez les textes un à un. Chaque texte indique ce qui est vrai avant l’étape, l’action, la donnée utilisée et le résultat observable.
Un texte pour tout le parcours
Décrivez toutes les actions et validations dans l’ordre. Le petit LLM propose le découpage ; vérifiez chaque opération avant de l’accepter.

Dans le mode formulaire, une carte représente une unité lisible et contient trois parties :

  1. Contexte local : nom, page courante et éventuel prérequis.
  2. Action : verbe contrôlé, cible et valeur.
  3. Validation : assertion, cible observée et résultat attendu.

Utilisez les flèches pour réordonner, le symbole de copie pour dupliquer et la croix pour retirer une carte. Préférez une action principale par étape. Un cas peut contenir des étapes sans assertion, mais il doit posséder au moins une validation observable.

Rôle des skills du petit LLM

Chaque mode sélectionne un contrat spécialisé : relecture des formulaires, analyse isolée des textes d’étape ou découpage du récit complet. Le modèle pose une question si une cible HTML, une donnée ou un contrôle manque. Il ne génère pas le code et ne confirme rien à votre place.

Ouvrez Voir le prompt et le skill utilisés sous le bouton d’assistance pour contrôler le nom du skill, les données analysées, le prompt exact et ses règles avant tout appel au modèle.

Exemple

Action
fill sur page:login#email avec {% raw %}{{data.email}}{% endraw %}.
Validation
value sur le même champ avec {% raw %}{{data.email}}{% endraw %}.

Étape 6

Paramétrer les données sans exposer de secret

Ajoutez les références une par une avec Ajouter une donnée. Placez ensuite la valeur dans l’action concernée. Les résultats attendus se saisissent dans le bloc Contrôle de chaque étape, au plus près de l’action qu’ils vérifient.

Trois espaces de noms sont disponibles :

{% raw %}{{data.email}}{% endraw %}
Colonne d’un CSV ou XLSX associé au cas.
{% raw %}{{data.login.email}}{% endraw %}
Colonne qualifiée lorsque plusieurs sources nommées participent au même cas.
{% raw %}{{fixture.customer_id}}{% endraw %}
Valeur reproductible non secrète fournie par une fixture.
{% raw %}{{secret.client_password}}{% endraw %}
Valeur résolue seulement dans l’environnement du runner.

Les références sont enregistrées et contrôlables ; les valeurs secrètes ne doivent apparaître ni dans le formulaire, ni dans le JSON, ni dans le code.

Pour plusieurs classeurs, choisissez une colonne clé stable et associez explicitement une ligne de chaque source à chaque cas. Ne comptez pas sur l’ordre des lignes : la matrice visible dans la structure de génération constitue la source de vérité.

Étape 7

Finaliser avec le LLM

  1. Vérifiez que l’intention fonctionnelle et le profil d’accès LLM sont sélectionnés.
  2. Lancez d’abord Analyser les informations manquantes et complétez les faits que vous connaissez déjà.
  3. Dans Dialogue avec le LLM, écrivez un fait métier ou demandez une relecture du brouillon.
  4. Pour démarrer rapidement, utilisez Développer le cas complet, Exploiter les champs HTML ou Renforcer les validations. Le texte reste modifiable avant envoi.
  5. Le LLM reçoit la structure courante, l’intention, le diagnostic et les capacités des pages analysées, jamais la seule conversation ni le HTML brut.
  6. Relisez chaque question et chaque proposition : libellé, justification, chemin structuré et nouvelle valeur.
  7. Cochez uniquement les opérations que vous acceptez. Une case non cochée est refusée lorsque vous appliquez le lot.
  8. Cliquez sur Appliquer la sélection. Le formulaire est mis à jour et la description est reconstruite depuis les seuls faits acceptés.
  9. Corrigez si nécessaire la description synthétique, puis relancez le dialogue si vous souhaitez une nouvelle revue.

Le LLM ne confirme jamais une hypothèse, un contrôle système ou une authentification. Une ligne restant dans Hypothèses ou ambiguïtés interdit de marquer le workflow comme confirmé.

Pourquoi la décision peut être refusée

Chaque lot mémorise l’empreinte du formulaire au moment de la réponse. Si vous modifiez le brouillon avant d’appliquer les propositions, relancez le dialogue : l’ancienne décision est bloquée pour ne pas écraser votre travail récent.

Ce que le LLM ne peut pas modifier

Les profils LLM et de génération, les pages analysées et la case Définition confirmée sont hors du contrat de proposition. Une réponse qui vise ces champs est rejetée en entier et ne laisse pas de message enregistré.

Quand le cas est suffisamment développé

Le cas doit décrire un comportement métier unique, référencer chaque élément manipulé depuis une page analysée, utiliser des références de données ou de secrets, contenir au moins une validation observable et ne plus conserver d’ambiguïté bloquante. Le LLM aide à atteindre cet état ; seul l’utilisateur accepte les faits et confirme ensuite la structure.

Étape 8

Vérifier la Structure de génération

Le panneau JSON est mis à jour pendant la saisie. Il contient la version du schéma, les profils, la préparation, le nettoyage, les politiques, les pages analysées et les étapes ordonnées. Il contient aussi llm_access_profile et code_generation_profile, ainsi que functional_intent. Elle conserve aussi authoring_mode, step_narratives et scenario_narrative. Utilisez Copier la structure pour l’inspecter à tout moment.

Avant confirmation, vérifiez :

  • qu’au moins une validation observable existe ;
  • que chaque action manipulant un élément possède une cible ;
  • que les valeurs dynamiques utilisent un espace de noms connu ;
  • que les secrets ne sont que des références ;
  • que les versions d’accès LLM et de génération sont cohérentes ;
  • qu’aucune hypothèse ne reste ouverte.

Étape 9

Enregistrer puis préparer la génération

  1. Cochez Définition confirmée après la revue.
  2. Enregistrez la définition structurée.
  3. Relisez la nouvelle version et son aperçu JSON.
  4. Ouvrez Voir les skills du prompt de génération pour vérifier les contrats et leurs sources.
  5. Utilisez Ouvrir le prompt de génération : un onglet séparé montre la demande exacte adressable au LLM, ses profils, ses skills, son contrat JSON et son empreinte.
  6. Contrôlez que les mots de passe sont remplacés par <secret-value-redacted> et qu’aucune clé API n’apparaît.
  7. Utilisez Télécharger le code généré depuis le cas confirmé. Le fichier est téléchargé sans afficher son contenu dans la page.
  8. La génération produit un artefact candidat, jamais une version approuvée automatiquement.
  9. Le candidat devra être exécuté individuellement avant approbation.
  10. Vérifiez le manifeste, puis utilisez le runner local pour obtenir JUnit et execution.json. Une modification du code impose une nouvelle génération.
